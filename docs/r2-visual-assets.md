# R2 thumbnails and static maps

The optional `s3`/`r2` visual store puts generated image bytes in object storage and keeps the existing asset identity, resource links, content type, size, object key, and SHA-256 in PostgreSQL. Existing API URLs remain valid. Once a verified object pointer exists and a public base URL is configured, image endpoints return a 302 to the immutable object URL. Unmigrated images continue to come from PostgreSQL.

## Release order

1. Build and review a release containing the R2 changes. This workspace also contains unrelated ongoing features; do not deploy the entire dirty checkout implicitly.
2. Apply `python -m db.migrations.add_visual_asset_object_storage` with `PYTHONPATH=backend` and the target database URL, **before starting the new application or workers**, even in database mode. It adds nullable pointer columns and permits null bodies; it neither rewrites nor deletes existing bytes. The migration has a five-second lock timeout and can be repeated.
3. Supply the dedicated credentials to both web and worker containers (and mirror publisher source environments). Keep the default database mode until credentials and schema are ready.
4. Start a reversible pilot with:

   ```dotenv
   VISUAL_ASSET_DURABLE_STORE=s3
   VISUAL_ASSET_S3_ENDPOINT=https://96d9819fafc99210217fc4e9aac9c73d.eu.r2.cloudflarestorage.com
   VISUAL_ASSET_S3_REGION=auto
   VISUAL_ASSET_S3_BUCKET=ogm
   VISUAL_ASSET_S3_PREFIX=assets
   VISUAL_ASSET_S3_RETAIN_DATABASE_BODY=true
   VISUAL_ASSET_REDIS_BODY_CACHE_ENABLED=false
   VISUAL_ASSET_CACHE_TTL_SECONDS=86400
   VISUAL_ASSET_PUBLIC_BASE_URL=
   ```

   Also supply `VISUAL_ASSET_S3_ACCESS_KEY_ID` and `VISUAL_ASSET_S3_SECRET_ACCESS_KEY` through runtime secrets. An upload must succeed and its metadata must verify before a database pointer is published. Leaving the public URL blank exercises authenticated R2 reads with PostgreSQL fallback during the pilot.
5. Confirm a newly generated thumbnail, resource map, and institution map work with Redis cold. Check pointer, object size/checksum, MIME type, and service logs. Verify the custom-domain TLS certificate and public GET before enabling `VISUAL_ASSET_PUBLIC_BASE_URL=https://assets.geo4lib.app`.
6. Make extensionless objects cacheable with a Cloudflare Cache Rule matching only `http.host eq "assets.geo4lib.app"` and `starts_with(http.request.uri.path, "/assets/")`: eligible for cache, respect origin Cache-Control, do not cache errors. Check a second successful GET returns `CF-Cache-Status: HIT`. Object URLs have one-year immutable cache headers; API redirects use a shorter TTL because legacy IDs can resolve to newly generated bytes.
7. Backfill in bounded batches. With the target database and R2 credentials in the process environment:

   ```sh
   PYTHONPATH=backend python backend/scripts/backfill_visual_assets_to_s3.py --limit 100
   PYTHONPATH=backend python backend/scripts/backfill_visual_assets_to_s3.py --apply --limit 100
   ```

   Dry-run is the default. Apply uploads each image, GETs and checks actual bytes, and conditionally commits a pointer only if the source body is unchanged. Re-running skips rows already copied. Use the returned `last_hash` with `--after` for paging; run again without a cursor at the end to catch concurrent changes. No bodies are removed. A failure is safe to retry, though it may leave an unreferenced immutable object.
8. After the production pilot passes, set `VISUAL_ASSET_S3_RETAIN_DATABASE_BODY=false` to stop retaining bytes on new writes. Remove historical bodies only through the checksum-gated procedure below, after all rows have durable pointers.

## Retention and disk headroom

Redis aliases receive a 24-hour TTL. New binary image cache writes are disabled in R2 mode by default. Existing non-expiring keys are unaffected. Redis DB 0 contains the Celery broker, and DB 1 also contains task results: never flush either database or apply indiscriminate eviction. Reclaim only positively identified visual cache keys whose durable copies have been verified, in small batches. Persisted RDB/AOF files may remain large until a planned rewrite; allow space for old and new files to coexist.

Do not expire R2 objects merely because they are old: current database links and published mirror manifests may still reference them. A future garbage collector should inventory references, include mirror releases, wait at least 30 days after objects become unreferenced, dry-run first, and delete only a reviewed manifest. Keep the seven-day incomplete multipart upload abort rule.

Removing PostgreSQL bytea values creates reusable database space but does not guarantee filesystem space is returned. Plan any table rewrite or repack separately with sufficient temporary disk and a lock/downtime budget. Avoid `VACUUM FULL` during reindexing. Keep production disk alerts and preflight checks independently of the image migration; Elasticsearch, logs, backups, and Redis persistence can still consume disk.

## Rollback

During the dual-write pilot, clear `VISUAL_ASSET_PUBLIC_BASE_URL` to stop redirects; set the durable store back to `database` only while every needed body is still present. Once any body is null, keep S3 reads enabled or restore those bytes before database-only rollback. Do not repoint the configured bucket or endpoint: persisted keys assume the same object store. Disabling redirects cannot instantly retract already cached immutable objects.

For DNS rollback, Porkbun's previous nameservers were `curitiba.ns.porkbun.com`, `fortaleza.ns.porkbun.com`, `maceio.ns.porkbun.com`, and `salvador.ns.porkbun.com`; the original records were retained there. Nameserver rollback also propagates gradually.

## Verified cleanup procedure

The copy-only utility bounds concurrency and shares a verified upload among rows with identical bytes. After a failed run, resume without `--after` so unfinished rows are included. Original bodies are retained.

Before cleanup, export the schema, generated asset metadata (excluding bodies), and resource links to a protected directory and copy them off the production host. Never place these backups in the public bucket. Switch all running application roles to `VISUAL_ASSET_S3_RETAIN_DATABASE_BODY=false` and stop dual-write canaries.

Run `verify_visual_assets_r2.py --manifest /protected/verified.jsonl --prune-postgres --workers 64` with the production environment. It refuses pruning while any pointer is missing, GETs and checksum-verifies every remote image, compares the existing local bytes, and fsyncs the audit manifest before each bounded cleanup transaction. Conditional updates protect concurrent changes. PostgreSQL uses the observed `xmin` row version, so even a concurrent body-only update prevents deletion without resending large image bodies in SQL; other database backends use byte equality. This guard was verified against a real concurrent update in an isolated PostgreSQL 15 instance. Metadata and resource links remain.

Then run `prune_verified_visual_redis.py --manifest /protected/verified.jsonl` for a dry run; add `--apply` after reviewing the counts. It touches only known binary image namespaces in DB 1 whose bytes match a verified object digest and size. Lua compare-and-UNLINK preserves values changed concurrently. It leaves broker queues, task results, image types, aliases, and unmatched data untouched.

Check filesystem headroom before ordinary PostgreSQL VACUUM and Redis persistence compaction. Run BGSAVE and BGREWRITEAOF one at a time and confirm persistence status before proceeding. Record actual filesystem space recovered, separately from logical body bytes released.

During DNS propagation, the old Porkbun zone also has an `assets` A record at `104.21.18.253` (TTL 600), matching Cloudflare's active edge. Cloudflare remains authoritative; this compatibility record serves clients with a cached old delegation.
